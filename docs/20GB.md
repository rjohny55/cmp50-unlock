## Validated hardware

Validated on 26–27 August 2026 with four cards:

```text
PCI device: 10de:1e09
subsystem:  10de:1554
VRAM:       20480 MiB per card
driver:     NVIDIA Open 610.43.03
kernels:    6.8.0-137-generic and 6.8.0-138-generic
BDFs:       01/02:00.0, 03:00.0, 81:00.0, 82:00.0
```

## Why the old patch did not boot the 20 GB board

The old path used WPR boundaries from the validated 10 GB card. Stock FWSEC
creates a different range on this 20 GB board:

```text
WPR high:low = 04ffee00:04ffe000
span         = 00000e00
```

The mismatch caused NVIDIA Booter error `0x8d`; GSP-RM then exhausted its boot
attempts and `nvidia-smi` found no devices.

The updated `01-cmp50-stockflow.patch` captures the stock FWSEC WPR range
separately for every PCI BDF, accepts only span `0xe00`, stores low/high in
per-BDF state, and fails closed if the geometry changes. It does not substitute
one card's fixed address and supports both the 10 GB and 20 GB layouts.

## Safe staged installation

Start with the most thoroughly validated 20 GB stage:

```bash
git clone https://github.com/rjohny55/cmp50-unlock.git
cd cmp50-unlock
sudo ./install.sh --stage rt --install-userland --initramfs
sudo systemctl poweroff
```

After the cold boot:

```bash
sudo ./verify-live.sh
```

Install ReBAR only as a separate next stage:

```bash
sudo ./install.sh --stage rebar --initramfs
sudo systemctl poweroff
```

After boot, validate both PCI Region 1 in `lspci -vv` and `BAR1 Memory Usage / Total`
in `nvidia-smi -q -d MEMORY`. Region 1 alone is not sufficient.

The complete Gen2 stage is restricted to the validated X99 host and exactly
kernel `6.8.0-137-generic`:

```bash
sudo ./install.sh --stage gen2 --allow-experimental-gen2 --initramfs
sudo systemctl reboot
systemctl status cmp50-gen2-second-pass.service
sudo ./verify-live.sh
```

The service must finish as `active (exited)` with a `PASS` message. The
installer refuses this procedure on kernel 138 and every other kernel.

## How the validated Gen2 path works

The first normal driver pass establishes the internal Gen2 policy. Before
Docker and the display manager start, `cmp50-gen2-second-pass.service` pauses
udev, unbinds only supported CMP50 PCI identities, unloads the NVIDIA modules,
performs FLR on every card, and loads the same module again.

The installed module parameters are:

```text
options nvidia cmp50_rebar_size=8 NVreg_RegistryDwords="RMPcieLinkSpeed=0x1;RmForceEnableGen2=0x1"
```

`RMPcieLinkSpeed=0x1` is NVIDIA's `ALLOW_GEN2_ENABLE` value. Value `0x2` means
disable and must not be substituted here.

During the second pass the endpoint requests Recovery first. After 50 ms the
root port requests Retrain. If the first two-second observation window ends at
Gen1, one identical retry is made. On the reference X99 host all four cards
complete as `RETRAIN_PASS attempt=201`; Link Disable is never used.

```text
01/02:00.0  Gen2 x4    20480 MiB  BAR1 16384 MiB
03:00.0     Gen2 x16   20480 MiB  BAR1 16384 MiB
81:00.0     Gen2 x16   20480 MiB  BAR1 16384 MiB
82:00.0     Gen2 x16   20480 MiB  BAR1 16384 MiB
compute     PASS_CMP50HX_ISSUE_RATE_AND_COUNTS
```

Firmware may enumerate the first card as `01:00.0` or `02:00.0`, so the helper
discovers BDFs dynamically. It checks exact device/subsystem IDs, FLR support,
GPU count, physical 5.0 GT/s link speed, and ReBAR encoding 14. It restores udev
and fails the service if any check fails.

FLR resets the physical ReBAR control to 256 MiB while Linux can retain the
already allocated 16 GiB resource. `03-cmp50-rebar.patch` handles only that
exact case: it re-arms BAR1 encoding 14 without moving the resource and verifies
the readback. Both PCI Region 1 and NVIDIA BAR1 then report 16 GiB.

## Kernel and host limitations

- The `rt` and `rebar` stages are validated on kernels 137 and 138.
- An earlier direct Gen2 boot on kernel 138 reproduced Booter error `0x8d`.
- Automated Gen2 is therefore enabled only for kernel 137 in `install.sh`.
- Gen2 is motherboard- and bridge-dependent; the X99 result is not a blanket
  claim for other hosts.
- Without `nvidia-persistenced`, closing a GPU client can briefly initiate
  another GSP/retrain cycle. `verify-live.sh` waits for the bounded retry before
  evaluating the final link state.
- The reported 56 RT cores are a host-side value. Real RT opcodes remain
  unavailable.

The longer investigation history and failed Link Disable experiments remain in
the [Russian 20 GB research log](20GB_RU.md). The current production path does
not use Link Disable.

## Idle governor

The optional scripts are in `idle-governor/`. They are not enabled by default
and have not yet been validated on the 20 GB system. Always confirm that full
clocks return under load before keeping the governor enabled.
