# CMP 50HX 20 ГБ

[Главная](../README_RU.md) · [Версия 10 ГБ](10GB_RU.md)

## Проверенное оборудование

Проверка выполнена 26–27 августа 2026 года на четырёх картах:

```text
PCI device: 10de:1e09
subsystem:  10de:1554
VRAM:       20480 MiB на каждой карте
driver:     NVIDIA Open 610.43.03
kernel:     6.8.0-137-generic и 6.8.0-138-generic
BDF:        01:00.0, 03:00.0, 81:00.0, 82:00.0
```

## Почему старый патч не запускал 20 ГБ

Старый путь использовал WPR-границы, соответствующие проверенной 10-ГБ карте.
На 20-ГБ плате штатный FWSEC создаёт другой диапазон:

```text
WPR high:low = 04ffee00:04ffe000
span         = 00000e00
```

Из-за несовпадения NVIDIA Booter завершался кодом `0x8d`, затем GSP-RM
достигал лимита попыток и `nvidia-smi` не видел устройства.

Обновлённый `01-cmp50-stockflow.patch` получает WPR после штатного FWSEC
отдельно для каждого PCI BDF, принимает только span `0xe00`, сохраняет
`low/high` в per-BDF state и останавливается при изменении геометрии. Это не
подстановка адреса одной карты, а динамический fail-closed путь для 10/20 ГБ.

## Безопасная установка

По умолчанию выбирается стадия `rt` — максимально проверенная на 20 ГБ:

```bash
git clone https://github.com/rjohny55/cmp50-unlock.git
cd cmp50-unlock
sudo ./install.sh --stage rt --install-userland --initramfs
sudo systemctl poweroff
```

После холодного старта:

```bash
sudo ./verify-live.sh
```

ReBAR устанавливается только следующим отдельным этапом:

```bash
sudo ./install.sh --stage rebar --initramfs
sudo systemctl poweroff
```

После старта одновременно проверьте `lspci -vv` Region 1 и
`nvidia-smi -q -d MEMORY` → `BAR1 Memory Usage / Total`. Только Region 1 = 16G
недостаточно: драйвер также должен сообщить большой BAR1.

## Gen2 — экспериментальный этап

`04-cmp50-pcie-gen2.patch` повторно открывает XVE PCIe shadow после GSP. Это
доказанно меняет endpoint `LnkCap` с 2.5 на 5 GT/s. Однако стандартный PCIe
Retrain не переводит физическую линию на тестовом X99 host. Полный Link
Disable/Enable переводит, но разрывает активный RM; безопасный двухпроходный
boot helper ещё разрабатывается.

На ядре `6.8.0-138` отдельно проверены стадии `rt`, `rebar` и `gen2`: первые
две запускают все карты, а прямая загрузка раннего Gen2-модуля с добавленным
`04` воспроизводимо завершает GSP Booter кодом `0x8d`.

26 августа 2026 UTC также проверена точная двухэтапная последовательность:
ранний v1 (`SHA256 e6988383...e220b5`) -> выгрузка -> по одному FLR каждой
карты -> текущий v2 (`SHA256 14f4cbe3...ac2ed4`). v1 завершился Booter
`0x8d`, после перехода v2 успешно поднял все четыре карты по 20480 МиБ без
нового Booter-сбоя. Однако у всех четырёх endpoint после GSP остались
`LnkCap=2.5 GT/s`, `Link Control 2 target=Gen1` и физический Gen1; журнал
сообщил `CMP50_GEN2: XVE shadow update failed`. Fail-closed барьер сработал,
поэтому Link Disable/Enable не выполнялся. Следующая задача — перенести либо
повторить запись XVE в фазе, где эти shadow-регистры ещё доступны, а не
обходить защитный барьер.

27 августа 2026 на ядре `6.8.0-137-generic` проверен следующий исследовательский
вариант. Сначала «primer»-модуль с исходной маской `0x00060000` выполнил
внутреннюю команду link-rate по `BAR0+0x8872c=6`. После его выгрузки внутренний
`PL_LINK_RATE` был `0x00250036`; FLR каждой карты изменил его на `0x00220036`.
Board-gated утилита затем успешно установила усиленную политику
`0x00240036` с маской `0x00160000`. Финальный модуль поднял GSP на всех четырёх
картах, сохранил 20 ГБ VRAM и 16 ГБ BAR1, а endpoint объявлял Gen2. Стандартный
Retrain bit по-прежнему вернул `RETRAIN_FAIL`.

После выгрузки финального модуля было выполнено ровно одно Link Disable/Enable
на каждом соответствующем root-port. Физические линии поднялись как Gen2 x4
для `01:00.0` и Gen2 x16 для `03:00.0`, `81:00.0`, `82:00.0`. Это доказывает,
что распаянные x16 платы и слоты способны работать в Gen2 x16.

Однако последовательность пока непригодна для постоянной установки: после
переключения мостов XVE-регистры BAR0 `0x88084/0x880a4/0x880a8` возвращали
`ffffffff`, из-за чего ReBAR probe остановился fail-closed и RM не смог
повторно привязать ни одну карту. Однократный FLR сохранил физический Gen2, но
XVE не восстановил. Повторное переключение root-port в том же старте не
выполнялось. Перезагрузка снова в ядро 137 восстановила четыре рабочие карты
по 20480 МиБ и BAR1 16384 МиБ, уже в Gen1.

Практический вывод: ядро 137 полезно для исследования и подтвердило саму
возможность Gen2, но возврат на него сам по себе не делает Gen2 готовым.
Нужен путь, который завершает переключение линии до зависимости RM/ReBAR от
XVE (например, pre-OS/UEFI), либо полноценная повторная инициализация GPU после
переключения моста. До этого автоматизировать Link Disable/Enable нельзя.

Это отличается от проверенной 10-ГБ последовательности автора. В текущем
upstream `04-cmp50-pcie-gen2.patch` не выключает линию: он выполняет внутреннюю
команду `0x8872c=6`, выставляет target Gen2 на endpoint и upstream bridge и
использует обычный Retrain bit, пока RM остаётся загруженным. На исходном
однокарточном AMD AB350 host это даёт `RETRAIN_PASS` и Gen2 x4. На нашем
четырёхкарточном Intel X99 тот же безопасный механизм возвращает
`RETRAIN_FAIL`; проблема появляется только при добавленном нами полном Link
Disable/Enable. Кроме того, upstream всё ещё содержит фиксированный 10-ГБ WPR
`0x027fe000..0x027fee00`, поэтому его успешный Gen2 не доказывает совместимость
всей последовательности с 20-ГБ WPR `0x04ffe000..0x04ffee00`.

Поэтому `install.sh --stage gen2` требует дополнительный флаг
`--allow-experimental-gen2`. Это не означает, что режим безопасен:
установщик не выполняет Link Disable и не включает Gen2.

`tools/cmp50-bar0-link-rate.c` — fail-closed исследовательская утилита для
внутренней команды link-rate. Она проверяет точные PCI/subsystem ID и считает
чтение `0xffffffff` ошибкой. Утилита ещё не является boot helper и не должна
запускаться автоматически.

`tools/cmp50-bar0-gen2-prepare.c` — второй board-gated исследовательский
инструмент для усиленной маски `PL_LINK_RATE` (`0x00160000`). Он требует явный
флаг `--apply`, проверяет точный PCI/subsystem ID, отказывается писать при
`0xffffffff` и проверяет readback. Это не установщик и не безопасная процедура
включения Gen2.

## Idle governor

Скрипты находятся в `idle-governor/`, но для 20 ГБ не включаются по умолчанию.
Обязательно проверяйте возврат полных частот под нагрузкой.
